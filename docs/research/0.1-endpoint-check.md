# 0.1: Do the usage endpoints answer directly?

Date: 2026-09-30. Evidence: one run of a read-only probe by the owner.

> **Superseded for Claude by [R8](R8-omp-authentication.md).** Anthropic's
> terms forbid third-party developers from collecting or intermediating
> Claude.ai credentials or session tokens. This probe was a one-off check
> the owner ran on their own machine. usage-watch must not read a Claude
> token to call this endpoint.

## Method

The probe read each harness's existing login token into memory, sent it
once to that provider's usage endpoint with the User-Agent
`usage-watch/0.1 (endpoint probe)`, and printed only status codes and the
response structure. Every text value was masked except reset timestamps,
and numbers were shown only under limit-like keys. No token was printed,
refreshed or written. Endpoints and headers come from OpenUsage's source
(MIT), at commit `ab3e87b`.

| Account | Token source | Endpoint | Result |
|---|---|---|---|
| Claude, personal plan | Claude Code's login (macOS Keychain `Claude Code-credentials`; `~/.claude/.credentials.json` elsewhere) | `GET https://api.anthropic.com/api/oauth/usage` with `anthropic-beta: oauth-2025-04-20` | **200** |
| Claude, team plan | omp's login (`~/.omp/agent/agent.db`, `auth_credentials`, provider `anthropic`) | same | **429** |
| Codex | `~/.codex/auth.json`, `tokens.access_token`, with `ChatGPT-Account-Id` from `tokens.account_id` | `GET https://chatgpt.com/backend-api/wham/usage` | **200** |

## Findings

**Claude and Codex usage can be read directly, without OpenUsage.** Both
answered 200 to a plain, honest User-Agent. Claude Code's User-Agent,
which OpenUsage sends, is not needed to read usage.

**Claude response.** Capacity windows are objects of
`utilization` (percent used), `resets_at` (ISO timestamp), and dollar
fields that were null on this plan:

- `five_hour`, `seven_day`: the session and weekly pools.
- Many model- or product-specific windows (`seven_day_opus`,
  `seven_day_sonnet`, and internal code names). Most were null; any may
  appear, so read them generically rather than by a fixed list.
- `limits[]`: a flattened list with `kind`, `group`, `percent`,
  `severity`, `resets_at`, `is_active`. It is probably the most stable
  shape to read, but that is unconfirmed.
- `extra_usage` and `spend`: paid-overage state, amounts in minor units
  with currency and exponent. Relevant to the cost phase.
- `seven_day_breakdown`: `rows[]` of `key`, `display_name`, `percent`, plus
  `window_started_at`. A per-category share of the weekly window, relevant
  to the usage phase.

**Codex response.** `rate_limit.primary_window` (5 hours) and
`rate_limit.secondary_window` (7 days), each with `used_percent`,
`limit_window_seconds`, `reset_after_seconds`, and `reset_at` (Unix
seconds). There are also `rate_limit.allowed`, `limit_reached`,
`model_usage` (availability by model), `credits`,
`rate_limit_reset_credits` and `chatpass.windows[]`. The response
includes `email`, `user_id` and `account_id`, which must never be stored or
shown (plan principle: privacy).

The numbers agreed with OpenUsage's report for the same accounts on the
same evening (Codex weekly 96% used; Claude personal 5-hour window freshly
reset).

**The team-plan token was throttled (429).** The request was identical to
the one that succeeded for the personal plan, so the User-Agent and
headers are not the cause. The usage endpoint limits each token itself.
omp polls this endpoint with the same token (its `usage_history` table),
and OpenUsage may too, so a third poller competes for the same allowance.
This is inferred, not confirmed.

## Consequences for the plan

- **C1 is viable** for the Claude personal plan and Codex.
- **Poll rarely, and back off on 429.** No more often than every few
  minutes per token, and honour `Retry-After` if present. Every tool
  polling the same token shares one allowance.
- **Team plan:** fall back to omp's `usage_history` (no token needed,
  refreshed roughly hourly), and retry the direct read on a long backoff.
- **0.2 (OpenUsage):** it can become optional rather than required. It is
  not yet safe to remove: the team-plan path isn't confirmed to work
  directly, and OpenUsage's own polling may be part of why it is throttled.

## Open
