# Prototype assumptions

Written while the owner was away (2026-10-01), to build the proof of
concept without blocking on decisions. **Each entry is an assumption the
owner should confirm or overturn.** Entries are added as the work goes;
none is a settled decision until the owner says so.

> **Nudging was removed on 2026-10-01** (see the plan's Decisions log).
> A1, A14, A15, A16, A17's nudging rationale, and A20's policy part are
> deferred with it. A17, A19 and A20's screen-side retry time still affect
> what is displayed. The rows stay as written.

| # | Assumption | Why | Where it bites if wrong |
|---|---|---|---|
| A1 | D8's defaults are adopted as written: `min_remaining_pct = 5`, `stale_window_fallback = off`, `stale_window_max_age = 60 min`, `stale_window_min_remaining_pct = 50` (unused while the fallback is off) | Conservative. With the fallback off, the policy waits rather than guessing | The nudge policy (F5) may wait more often than you'd like |
| A2 | The proof-of-concept scope is the plan's: F4 and F5, C1 (capacity from credential-free sources), C2 (usage from session logs), V1 (usage breakdown), V2 ("since I last looked"), A1 (pool alerts). The OTLP receiver (C3), cost pricing (K), hooks (H) and export (E) are out | The plan's Scope section | Nothing |
| A3 | The Claude status line tap is **built but not installed**. `init --claude-statusline` shows the change and only applies it on confirmation. The prototype reads Claude capacity from `~/.claude.json` `cachedUsageUtilization` in the meantime | Installing it edits your Claude Code settings. That's yours to approve (an open decision in the plan) | Claude capacity is only as fresh as the last time `/usage` was opened, until the tap is installed |
| A4 | No background process is started on your machine. `run` works, but you start it | Claude Code's own permission checks block detached processes, and starting one is your call | Nothing collects until you run it |
| A5 | Collectors read only fields confirmed from real files on this machine (key names only, never content). Any field still unconfirmed is left out, and listed here | D4's rule: "to confirm from a recorded sample" | Some columns stay null in the prototype |
| A6 | Attribution subjects whose table assigns a surrogate id on insert (capacity samples, limit events) are referred to by their natural key as `subject_id`: `source\|stream_key\|window\|observed_at` and `source\|stream_key\|source_key` | Collectors never touch the store, so they can't know surrogate ids; natural keys are unique by construction (D3) | A later schema could switch to surrogate ids with a one-off rewrite |
| A7 | A minimal pane-to-session join (D2's Claude `~/.claude/sessions/<pid>.json` and omp `terminal-sessions/tmux-%N` methods) is pulled forward from C4 into the prototype | Without it the D8 nudge policy can't find a pane's account and would always wait | Only those two methods; Codex panes stay unjoined (their lsof method is later) |
| A8 | Cost events are not emitted; harness cost figures stay in an observation's `native` numbers | Cost is outside the proof-of-concept scope (A2), and request-scoped cost needs the event id assigned at write time | No cost views in the prototype |
| A9 | `init --claude-statusline` writes the absolute path of `usage-watch` into the status line command when it can find one | Claude Code runs the status line with its own PATH; a bare name could break the status line | If usage-watch is later moved, rerun init |
| A10 | omp's own side calls (`type:"model_usage"`: judging, auto-thinking, find, unexpected-stop, cache-warm) are ingested as **auxiliary** usage, keyed `aux:<id>` | They consumed capacity, so they belong inside totals (D1 invariant 3); views can filter them | 6,402 such calls on this machine; excluding them would under-count omp's usage |
| A11 | Every Claude transcript observation shares one stream (`claude.transcript:all`), not one per session; a request stays with the session it was first seen in | A resumed or forked session copies earlier history; per-session streams counted 232 requests twice on this machine. `message.id + requestId` is unique across sessions | A copied request is attributed to its original session, not the copy |
| A12 | A Codex token event without `cache_write_input_tokens` is read as 0 for that field | D4 allows "omission means zero" with evidence: all 19,403 events that carry it are 0, and OpenAI caching has no separate write step | Without it, 11,980 older Codex events would have an unknown total input |
| A13 | Known prototype limits: the first backfill takes about 2.5 minutes over this machine's history; tail watermarks are JSON maps rewritten each pass (omp's is about 815 KB) | Correct and simple; incremental passes take well under a second | Worth optimising if history grows much larger |
| A14 | D8 window discovery counts as **complete** for `omp.usage_cache`, `claude.cached_utilization` and `codex.rollout`, and **partial** for `claude.statusline` | Each complete source lists every window its account has (omp's report enumerates its limits; Claude's cache carries the per-model windows; Codex's rate limits carry primary and secondary, and its other limit types are windowless). The status line shows only 5-hour and 7-day. Strict D8 with nothing complete would never nudge Claude or Codex | A missed window would let a nudge through while that window is exhausted; the pane would simply stall again and escalate |
| A15 | Known issue: the nudge policy and the screen collector each derive a stall id, by slightly different recipes (session or pane versus pane plus process id). "Nudge once" is enforced by both, so no stall is nudged twice | Built in parallel against D8's definition; both fit it | Should be unified so a stall has one id everywhere |
| A16 | `run --no-nudge` records no policy decisions | D3's "collect only": the policy runs view-only and writes nothing | No record of why a pane waited while collecting only |
| A17 | omp's two identifiers for one account (its login `identity_key` and its usage report's account id) are merged as **co-reported**, verified by a check run on this machine: for every usage report, `email:<email>\|org:<orgId>` from the report equals a stored `identity_key` (compared as hashes; no value printed) | Without it a pane's account (from its login) never matched the pools (from the reports), so omp panes could never be nudged | The merge is reversible (`account_merges`); a wrong merge would pool two accounts' capacity |
| A18 | Known limit: a resumed Claude Code conversation gets a new session id, but Claude's per-process session file keeps the old one, so the pane joins a session that looks quiet and gets no live account | Seen on this machine; it's Claude Code's data, not usage-watch's | Such panes wait (fail-safe); Claude Code often resumes by itself anyway |
| A19 | A live pane's account is resolved **at the decision time** (D2's rule applied to "now"), not over the session's whole span. omp emits account evidence at each login switch, so the account in use now is unique even when the session as a whole is ambiguous | omp rotates logins within one session; session-level attribution was ambiguous for most omp panes | Views of history still show such sessions as ambiguous, which is correct |
| A20 | A stall whose harness states a retry time (omp's `retry-after-ms`, pinned to the stall's onset) waits until that time, whatever the anchors say. **Also corrects A14 for omp**: its usage report does not list every limit; a live 429 asked for 2.4 hours while every listed window was clear | Found by checking the policy's first live "nudge" verdict against the pane's own screen before trusting it | Without it the policy would nudge into a limit the report doesn't show |
